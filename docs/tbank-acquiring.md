# Интернет-эквайринг Т-Банка: разбор документации и план интеграции

Разбор от 21.09.2026 по https://developer.tbank.ru/eacq/ и официальной спецификации
`/schemas/eacq/openapi.yaml` v1.32 (при расхождении с текстом документации приоритет у
спецификации — так написано в самой документации). Каждый критичный факт перепроверен
по первоисточнику независимо: 110 подтверждено, 2 уточнены, 1 не подтверждён.
Ключи DEMO-терминала проверены живым вызовом Init → GetState → Cancel.

Заменяет CDEK Pay (`app/services/cdek_pay.py`), который так и не был включён.

## 1. Адреса и окружения

| Что | Адрес |
|---|---|
| API (и боевой, и DEMO-терминал) | `https://securepay.tinkoff.ru/v2/<Метод>` |
| Тестовый сервер | `https://rest-api-test.tinkoff.ru/v2/` — только боевой терминал **без** DEMO и только с IP из белого списка (подаётся через чат ЛК). Нам не нужен. |
| Платёжная форма | `https://pay.tbank.ru/...` (приходит в `PaymentURL`) |

- Домена tbank для API нет — API остаётся на tinkoff.ru.
- **DEMO-терминал работает на боевом адресе** — проверено вызовом.
- Методы СБП (`GetQr`, `GetQrState`, `SbpPayTest`, `GetQrBankList`) и `/cashbox/SendClosingReceipt`
  есть только на боевом адресе.
- POST + `Content-Type: application/json`, TLS 1.2+, имена полей регистрозависимы, валюта — рубли.
- Бизнес-ошибки приходят с HTTP 200 и `Success=false`; системные — HTTP 500, `ErrorCode` 9999.

### TLS: сертификаты НУЦ Минцифры
**Уже переведено:** на 21.09.2026 `securepay.tinkoff.ru` отдаёт цепочку Russian Trusted
Sub CA (проверено и с Windows, и из контейнера прода) — голый httpx падает на «self-signed
certificate in certificate chain». Корневой и промежуточный сертификаты лежат в
`app/certs/russian_trusted_ca.pem` (корень до 2032-02-27, промежуточный до 2027-03-06 —
**обновить до марта 2027**) и подключаются только к клиенту Т-Банка, **в объединении с
certifi** (`tbank_ssl_context()`), чтобы не потерять доверие к публичным УЦ. Отключать
проверку TLS нельзя.
Когда на НУЦ переведут и платёжную форму, покупатели в Chrome/Safari/Firefox увидят
предупреждение — это общая проблема всех мерчантов, на нашей стороне не решается.

## 2. Подпись Token

**Запрос:** корневые скалярные поля запроса (без `Token`; вложенные объекты и массивы —
`Receipt`, `DATA`, `Shops` — не участвуют) + пара `Password` → сортировка по ключу
(с учётом регистра) → склейка **только значений** без разделителей → SHA-256 от UTF-8 → hex.

Эталон из документации (проверен): строка
`19200Подарочная карта на 1000 рублей0000011111111111111MerchantTerminalKey` →
`72dd466f8ace0a37…`. Итоговый JSON на той же странице несогласован с хешем — тестировать
только по строке.

**Уведомление:** то же самое, по **всем фактически пришедшим** корневым скалярам, кроме
`Token` (вложенные `Data`, `Receipt` не входят). Набор полей не фиксирован: зависит от способа
оплаты (у СБП нет `CardId`/`ExpDate`, при рекуррентах есть `RebillId` и т. д.) — список не
хардкодить.

Грабли:
- булевы — строго `"true"`/`"false"` (Python `str(True)` = `"True"` ломает подпись);
- числа — десятичной строкой без `.0` (не парсить JSON так, чтобы int стал float);
- `null`-поля в подпись не входят;
- сравнивать через `hmac.compare_digest`;
- `Receipt` в подпись не входит, так что состав чека подписью не защищён.

## 3. Основной поток (одностадийная оплата)

`Init` → покупатель платит на `PaymentURL` → уведомление `CONFIRMED` → услуга.

**Init** — обязательные: `TerminalKey`, `Token`, `Amount`, `OrderId`. Полезные: `Description`
(≤140 символов; при СБП показывается в мобильном банке), `PayType` (`O` — одностадийная),
`NotificationURL`, `SuccessURL`, `FailURL`, `RedirectDueDate` (срок жизни ссылки/QR, от 1 минуты
до 90 дней), `DATA` (≤20 пар, ключ ≤20, значение ≤100 символов), `Receipt`.
- `Amount` — целое, **в копейках**; должен точно равняться сумме `Amount` позиций чека.
- `OrderId` ≤50 символов, уникален для каждой операции. Идемпотентность повторного Init
  с тем же OrderId **не описана** — защищаемся у себя.
- Ответ: `Success`, `ErrorCode`, `Status`, `PaymentId` (**строка**, хранить как TEXT), `PaymentURL`.

**Статусы.** «Деньги получены» = **`CONFIRMED`**; `AUTHORIZED` — лишь блокировка. Колонка
«Конечный» в справочнике статусов противоречива (NEW, AUTHORIZED помечены конечными) —
по ней логику не строить. Отмена/возврат: `REVERSED`, `PARTIAL_REVERSED`, `REFUNDED`,
`PARTIAL_REFUNDED`; промежуточные `REVERSING`, `REFUNDING`, `ASYNC_REFUNDING`; неуспех —
`REJECTED`; `DEADLINE_EXPIRED` (включается через чат ЛК).

**Решать об оплате только по `Status`.** Для СБП, T-Pay, SberPay и др. неуспех приходит как
`Success: true`, `ErrorCode: "0"`, `Status: "REJECTED"`. Плюс по требованию раздела
«Безопасность» сверять `Amount`, `OrderId`, `TerminalKey` с нашим заказом; при
расхождении услугу не выдавать.

**Тело уведомления подделывается при верной подписи** (найдено ревизией): подпись склеивает
значения без разделителей и не фиксирует набор полей. Например, `PaymentId="…PARTIAL_"` +
`Status="REFUNDED"` подписан так же, как `PaymentId="…"` + `Status="PARTIAL_REFUNDED"`, а цифры
из конца `Pan` можно «сдвинуть» в начало `PaymentId`. Поэтому у нас уведомление — только
сигнал, решение — по `GetState` (ответ по TLS от банка; в нём есть `OrderId` — сверяем).

## 4. Уведомления (вебхук)

- POST JSON на `NotificationURL` (из Init, иначе из настроек терминала).
- **Уведомления о фискализации (`Status: RECEIPT`) идут только на URL из настроек терминала** —
  значит, URL в ЛК обязан указывать на наш обработчик.
- Ответ: **HTTP 200, тело `OK`** латиницей, без тегов и JSON. На странице тест-кейсов «ОК»
  набрано кириллицей — копировать оттуда нельзя, иначе повторы на месяц.
- Ждут ответа 10 секунд. Наш обработчик внутри делает один `GetState` (таймаут клиента
  10 с, обычно ответ за доли секунды); если банк не ответил — отдаём 503, и банк повторит.
- Повторы: раз в час 24 часа, затем раз в сутки месяц; архив 90 дней с повторной отправкой.
- При одностадийной оплате **`AUTHORIZED` и `CONFIRMED` шлются одновременно** — возможен
  обратный порядок. Переходы монотонные (AUTHORIZED после CONFIRMED не откатывает),
  блокировка строки платежа. Журнал уведомлений — по хешу тела (повтор банка приходит тем же
  телом); на решения ключ не влияет — состояние всё равно берётся у банка.
- Сети отправителя: `91.194.226.0/23`, `91.218.132.0/24`–`91.218.135.0/24`, `212.49.24.0/24`,
  `212.233.80.0/24`–`212.233.83.0/24`; тестовая среда — `91.194.226.181`.
- В уведомлении `Data` (не `DATA`), `Pan` маскированный (у СБП — телефон).

## 5. СБП

- Покрывается платёжной формой (`PaymentURL`): там карта, СБП, T-Pay, SberPay — набор
  включается в ЛК, блок «Готовая платежная форма».
- Своя форма: `Init` → `GetQr` (`DataType`: `PAYLOAD` — ссылка, `IMAGE` — SVG; с `BankId` —
  диплинк в приложение банка). Список банков — `GetQrBankList` (при своём списке — правила
  отображения НСПК).
- Ограничения: минимум **10 ₽**, только одностадийная оплата, **не работает в схеме
  «Маркетплейс»**, **нужен расчётный счёт в Т-Банке как счёт для возмещений**.
- Чек формируется автоматически только при оплате по динамическому QR (через Init).
- Тест СБП — DEMO-терминал на боевом адресе (`SbpPayTest`).

## 6. Мобильное приложение

- **Мобильные SDK эквайринга отключены с 1 марта 2026.** Единственный способ — открыть
  `PaymentURL` в Chrome Custom Tabs (Android) / SFSafariViewController (iOS).
  UIWebView/WKWebView использовать нельзя.
- Терминал перевести на тип подключения «Универсальное».
- Обязательны `SuccessURL`/`FailURL`; после возврата в приложение — `GetState` (через наш бэкенд).
- Пароль терминала в приложение не класть: к API Т-Банка ходит только наш сервер.
- Flutter: `url_launcher` с `LaunchMode.inAppBrowserView`.

## 7. Чеки 54-ФЗ

- Т-Банк сам чеки не пробивает: либо сервис «Чеки Т-Бизнес» (без абонентки, **комиссия
  1,5% с платежа**; пробивает CloudKassir по агентской схеме со своей СНО — ОСН; **не подходит
  при агентском бизнесе**), либо своя облачная касса партнёра.
- `Receipt` обязателен в Init, если к терминалу подключена касса. Обязательные поля:
  `Items`, `Taxation`, `Email` или `Phone`.
- `Taxation` — ровно 5 значений: `osn`, `usn_income`, `usn_income_outcome`, `esn`, `patent`.
- `Tax` — `vat20`/`vat120` **убраны**, есть ставки 22%, 5%, 7%; для УСН без НДС — `none`.
  Пример Init в самой спецификации до сих пор содержит `vat20` — не копировать.
- `PaymentMethod`: для полной предоплаты — `full_prepayment` (по умолчанию `full_payment`).
  `PaymentObject`: `service` (в ФФД 1.05 по умолчанию `commodity`).
- `Price`, `Amount` позиции — копейки; `Amount = Quantity × Price`; сумма позиций = `Amount` платежа.
- ФФД: в ЛК по умолчанию 1.05; на 1.2 переключаться до первых чеков; если версии в кассе и
  ЛК не совпадают — чеки не уходят. Для B2B (наименование и ИНН покупателя) нужен ФФД 1.2.
- **Предоплата → два чека**: при оплате — «предоплата 100%», при оказании услуги — закрывающий
  (`POST /cashbox/SendClosingReceipt`). У нас оплата и выдача документов разнесены во времени.
- Возврат: полный — `Receipt` не передаём (чек сформирует Т-Банк); частичный — `Receipt` только
  с возвращаемыми позициями.
- Уведомление о фискализации — отдельное, `Status: RECEIPT`, только на URL из ЛК.
- Штрафы: ошибка в реквизитах 5–10 тыс. ₽; непробитый чек — 75–100% суммы, не меньше 30 тыс. ₽.

## 8. Возвраты

- Один метод `Cancel` (`TerminalKey`, `PaymentId`, `Token`; `Amount` для частичного;
  `ExternalRequestId` — ключ идемпотентности возврата).
- Из `AUTHORIZED` — снятие холда (бесплатно), из `CONFIRMED` — возврат (комиссия эквайринга
  не возвращается). Деньги берутся со счёта мерчанта/из возмещения; не хватит — отказ.
- СБП: возврат асинхронный (статус — `GetQrState`), НСПК пускает ≤1 неудачной попытки в час
  и ≤5 в сутки на операцию; нужен счёт в Т-Банке (ошибка 3038).
- Финал возврата — уведомлением (`REFUNDED` / `PARTIAL_REFUNDED`, неуспех — `REJECTED`),
  синхронный ответ Cancel ещё не означает, что деньги вернулись. Сумма в уведомлении о
  возврате (возврат или остаток) не документирована — остаток даёт `NewAmount` в ответе Cancel.
- **У нас через систему — только полный возврат.** У уведомлений о возврате нет id операции,
  и два частичных возврата банк описывает неотличимо; частичные делаются в ЛК Т-Бизнеса (там
  же банк соберёт чек), а увидев `PARTIAL_REFUNDED`, система шлёт админу просьбу сверить.

## 9. Что сделано в нашем коде (ветка `feat/tbank-acquiring`)

Главный принцип (две ревизии): **решения о деньгах — только по состоянию, которое банк
отдаёт сам** (`GetState` или ответ на наш `Cancel`), и только под `FOR UPDATE` строки платежа.

| Где | Что |
|---|---|
| `app/services/tbank_acquiring.py` | подпись, `Init` / `GetState` / `Cancel`, TLS-контекст с НУЦ, предохранитель (бизнес-отказы в него не копятся) |
| `app/services/tbank_payments.py` | автомат `apply_bank_state`: переходы только вперёд; `CONFIRMED` с чужой суммой не засчитывается (алерт один раз); `CONFIRMED` по «мёртвому» у нас платежу засчитывается — деньги реальные; «оплатил в момент закрытия ссылки» → «оплачен и возвращается», заявка ждёт; `recheck_payment` — сверка со слотом (атомарный UPDATE + SKIP LOCKED) и отпечатком платежа |
| `POST /webhooks/tbank/notification` | подпись и терминал → 403; `RECEIPT`/привязки — в журнал; найти платёж → блокировка → `GetState` → автомат → `OK` |
| `POST /payments/initiate` | один активный платёж на заявку (частичный уникальный индекс + обработка гонки); просроченная ссылка: `GetState` → если денег нет, `Cancel` → новая ссылка; платящуюся прямо сейчас не трогаем; неизвестный статус банка — 409, а не `Cancel` вслепую |
| `POST /payments/{id}/cancel` | только по `GetState`: оплаченное — засчитываем (Cancel был бы возвратом), платящееся — 409 |
| `POST /payments/{id}/refund` | только полный; `ExternalRequestId = refund:<id>:<попытка>`, повтор незавершённой попытки — тем же ключом (банк не вернёт дважды), новая попытка — только после окончательного отказа (`REJECTED` или отказ + `GetState` показывает оплату без возврата) |
| DEMO-терминал на проде | платить могут админы и тестировщики с подтверждённой почтой (`TBANK_TEST_PAYER_EMAILS`); ссылку DEMO остальным не показываем; даже оплаченная DEMO-ссылка не переводит заявку в «оплачена», если её создал не тестировщик |
| `scripts/reconcile_tbank_payments.py` | крон раз в 10 минут (`deploy/setup-ops.sh`): открытые ссылки, возвраты «в пути» и ссылки, закрытые только у нас |
| миграция 0034 | колонки платежа, `CHECK` на возвраты, два частичных уникальных индекса; даунгрейд при наличии платежей `tbank` отказывает явно |
| `scripts/deploy.sh` | миграции — новым образом **до** переключения контейнеров |

Проверки: юнит-тесты `tests/test_tbank_*.py` (подпись, автомат, приёмник, роутер; мутационно
проверено, что ключевые защиты ловятся) и смоук `scripts/smoke_tbank.py` — настоящий Postgres
+ живой DEMO-терминал (Init, GetState, Cancel), «оплата» имитируется подменой ответа банка
по конкретным PaymentId. Смоук уже поймал два бага, которые подставная сессия не видит
(обращение к устаревшим после rollback объектам при двойном «Оплатить»).

Не сделано (следующие шаги): кнопка «Перейти к оплате» на вебе (и убрать автосоздание
платежа при открытии карточки), «Оплатить» в мобильном приложении (Custom Tabs /
SFSafariViewController), чеки 54-ФЗ (`Receipt` — ждём ответов по кассе, СНО, НДС),
закрывающий чек при выдаче документов.

## 10. Открытые вопросы (к владельцу и бухгалтеру)

1. Какая касса: «Чеки Т-Бизнес» (1,5% с платежа) или своя облачная? Какой ФФД в ЛК?
   Привязана ли касса к DEMO-терминалу (проверочный Init прошёл без чека — похоже, нет)?
2. Система налогообложения ООО (`Taxation`) и ставка НДС (`Tax`).
3. Два чека (предоплата + закрывающий при выдаче документов) — подтвердить у бухгалтера.
4. Расчётный счёт ООО в Т-Банке установлен как счёт для возмещений (нужно для СБП)?
   Магазин подключён обычной схемой, не «Маркетплейс»?
5. Боевой пароль терминала — только в `.env.production` на сервере, не в переписку.
